# 与上游的接入关系

> 机制层文档：**我们怎么接进 vLLM / vllm-ascend，以及什么算越界**。
> 不含代码、不含函数名——它们随上游版本变，写进来文档就腐化。

---

## 1. 前提：不改上游源码

三条允许，一条禁止。

| 允许 | 说明 |
|---|---|
| **安装期注册入口** | 我们作为已安装的包，在包元数据里声明一个入口；上游启动时按名字调用它。**磁盘上没有任何上游文件被改。** |
| **启动期换表** | 上游决定"用哪个实现"靠查表。我们在它查表之前把表项换掉。 |
| **包装方法** | 上游某个决策方法返回什么，决定走哪条路。我们包住它，在特定条件下返回我们的东西。 |

| 禁止 | 为什么 |
|---|---|
| 改上游文件 | 一改就必须维护分支；这是 optimum-habana 那条路的起点，也是它停服的原因 |

**界线**：如果一件事只能靠"改文件"做到，说明位置接错了，应该重新找接入点。

---

## 2. 两个入口组，我们只占一个

上游有两组插件入口，回答的是完全不同的问题：

| 入口组 | 回答什么 | 谁占 | 结论 |
|---|---|---|---|
| **平台组** | "这台机器是什么平台" | **始终归厂商**（昇腾上是 vllm-ascend） | 我们不注册 |
| **通用组** | "这个进程里要装什么" | 我们 | 我们只注册这个 |

**为什么平台组不能碰**：

1. 一个进程只允许**一个**平台激活。厂商已经占了。
2. 我们再去注册，两个都声称"我能跑"时，本地会直接拒绝启动——整条栈起不来。
3. "我注册，但返回的还是厂商那个类"**不能免掉这个冲突**：冲突发生在"谁被激活"这一步，
   不在"返回的是谁的类"。
4. 收益是零：返回厂商的类等于什么都没做，却多背了一个会让全栈起不来的风险。

**通用组的行为**：上游在**每个进程**里调用一次（服务进程、引擎进程、每个 worker、
以及模型架构探测子进程）。由此得到两条必须遵守的事实：

1. **注册必须早于任何查表**——模型构造时会查表，表没写好就等于没接上。
2. **同一个函数会在同一台机器上被调用多次**（多进程），必须幂等。

## 3. 模型配置在什么时候能拿到

| 时机 | 能拿到什么 | 能不能做决策 |
|---|---|---|
| 命令行阶段（进程还没起） | 模型目录里的配置、本机能力 | ✅ 最好：能给人读的错误，能拒绝启动 |
| 插件入口（进程启动） | 环境变量、命令行残留、本机能力 | ⚠️ 只能"读计划、准备换表" |
| **模型加载前** | 完整模型配置 + 并行配置 + KV 预算 | ✅ **最后一次能安全改表的时机** |
| 算子实例化时 | 类名与构造参数 | ❌ 太晚，只能做局部断言 |
| 首次前向 | 真实形状 | ❌ 图可能已捕获 |

所以分工是固定的：**命令行阶段做决策 → 落成计划文件 → 入口读计划 → 模型加载前用真配置
交叉校验 → 之后只做断言。**

入口函数是**无参**的，它拿不到模型配置。所以"用真配置校验"这件事**不可能**在入口里完成，
只能挂到"模型加载前"。

## 4. 六个接入点（按机制分类）

按"对象"数会更多，但同一机制接管多少个对象**不增加成本**——这是接入点按"机制"计数的原因。

| # | 机制 | 解决什么 | 越界的风险 |
|---|---|---|---|
| 1 | **实现替换表** | 算子、层：让上游的类名解析到我们的实现 | 低（官方机制）；同名冲突时是断言而非覆盖 |
| 2 | **方法包装** | 上游用普通函数或方法的地方（补第 1 项够不到的面） | 中：包错层级会静默失效 |
| 3 | **模型替换表** | 整个模型类（路线 O） | 低；同名会静默覆盖，必须留日志 |
| 4 | **注意力后端选择** | 决定用哪个注意力后端 | 中：上游有缓存，晚了无效 |
| 5 | **插件入口** | 让我们在正确时机被调用 | 低 |
| 6 | **图捕获钩子** | 捕获前完成桶规划、捕获后确认零回退 | 中：捕获后不可再改 |

**预算：6 个机制，上限 8。** 超了要写例外说明并重新设计——这个数字是"还能每次上游升级都
全量验证"的边界。

## 5. 入口函数的职责与红线

入口函数（install）只做一件事：**按计划把表换掉，并确认换上了。** 顺序固定：

```
1. 读计划 ──── 没有 → 直接返回（不注入，厂商原样跑）
2. 版本门 ──── 与计划记录的三件套版本不一致 → 不注入
3. 显式开关 ── 被要求禁用 → 不注入
4. 按计划换表 ─ 每一项独立、可单独关：实现表、模型表、注意力后端、方法包装
5. 探测生效 ── 断言每一项真的换上了（不靠推理）
6. 查内核缓存 ─ 计划要的内核都在缓存里？缺 → 不注入，并提示去跑构建
7. 记摘要 ──── 一行：注入了哪几项、跳过了哪几项、为什么
```

四条红线：

| 红线 | 原因 |
|---|---|
| **不拿配置做决策** | 入口无参，此刻没有模型配置；决策在部署期已定 |
| **不编译内核** | 入口在每个进程都会跑；编译会占住解释器（实测能把引擎卡死） |
| **绝不向外抛异常** | 上游只 catch 模块导入，**不 catch 入口函数的执行**；抛出去 = 整个进程起不来 |
| **幂等且可卸载** | 多进程各跑一次；每个接入点都要能单独摘掉、单独验证 |

第三条最容易被忽略：**我们这层失效时，厂商路径必须照常能跑。** 所以内部兜住一切异常，
失败就记日志并返回"不注入"，而不是让异常穿出去。

## 6. 四个已知陷阱

0. **上游只 catch 导入，不 catch 执行。** 我们的包 import 失败 → 上游记日志继续（厂商照跑）；
   入口函数抛异常 → 进程直接起不来。见 §5 第三条红线。
1. **同名替换是断言，不是覆盖。** 上游生态里若已有同名实现（vllm-ascend 会注册一批），
   再注册会直接抛错。要么换名，要么直接写表——后者要收敛成**一个**函数，并在日志里写明"接管自谁"。
2. **注意力后端的选择有缓存。** 第一次取完就定死；之后再包装无效。必须在任何前向之前完成。
3. **子类覆盖会吃掉包装。** 昇腾上实际运行的是子类；若子类自己重写了我们要包的方法，
   包基类不生效。要么包实际类，要么在探测阶段发现。

---

## 7. 不靠相信，靠探测

换完表必须立刻验一遍，并在运行期计数：

| 探测 | 验什么 |
|---|---|
| 表项断言 | 我们写进去的条目确实是我们的实现 |
| 注意力后端 | 解析出来的类确实是我们 |
| 平台方法 | 被包装的方法确实换成了我们的 |
| 运行期打点 | 首次前向真的进了我们的实现（表对了但实例没创建是可能的） |
| 回退计数 | 稳态为 0；不为 0 就是缺陷 |

历史上出过"表写对了、进程里却看不到"的事故，原因至今没有完全定论。
**所以这一层不依赖推理，只依赖探测结果。**

## 8. 与 vllm-ascend 的分工

| 归它 | 归我们 |
|---|---|
| **平台槽位**（谁回答"这台机器是什么平台"） | 通用插件槽位 |
| 设备、上下文、流、worker、显存、KV 池分配、图捕获、通信 | 模型声明、决策、契约、实现提供者、内核 |
| 已经适配的模型与算子 | 它没适配的模型与算子 |
| 平台能力探测的**事实来源** | 用这些事实做选择 |

一条判据：**凡是"一个进程只能有一个"的东西，归它。** 平台就是这种东西。

---

## 9. 版本三角

引擎、平台、运行时三者的版本组合必须与计划文件里记录的一致。不一致就**不注入**并把差异打印出来——
不允许"先跑跑看"，因为不一致的表现通常是**数值错**而不是崩溃。

---

## 10. 和 v2 的关系

v2 的做法是自己实现平台层（不装 vllm-ascend），因此它必须占住平台槽位。
v3 把这个前提反过来：**平台槽位归上游，我们只占通用槽位。**

v2 的接入经验仍然有效（哪些地方必须 hook、哪些地方 hook 了也没用），
但代码形态不作数——`tileinfer/vllm/` 是 v2 形态，重构计划见架构文档的里程碑。
