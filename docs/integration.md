# 与上游的接入关系

> 机制层文档：**我们怎么接进 vLLM / vllm-ascend，以及什么算越界**。
> 不含代码、不含函数名——它们随上游版本变，写进来文档就腐化。

---

## 1. 前提：不改上游源码

三条允许，一条禁止。

| 允许 | 说明 |
|---|---|
| **安装期注册入口** | 我们作为已安装的包，在包元数据里声明一个入口；上游启动时按名字调用它。**磁盘上没有任何上游文件被改。** |
| **启动期换表** | 上游决定"用哪个实现"靠查表。我们在它查表之前把表项换掉。 |
| **包装方法** | 上游某个决策方法返回什么，决定走哪条路。我们包住它，在特定条件下返回我们的东西。 |

| 禁止 | 为什么 |
|---|---|
| 改上游文件 | 一改就必须维护分支；这是 optimum-habana 那条路的起点，也是它停服的原因 |

**界线**：如果一件事只能靠"改文件"做到，说明位置接错了，应该重新找接入点。

---

## 2. 两个入口组，我们只占一个

上游有两组插件入口，回答的是完全不同的问题：

| 入口组 | 回答什么 | 谁占 | 结论 |
|---|---|---|---|
| **平台组** | "这台机器是什么平台" | **始终归厂商**（昇腾上是 vllm-ascend） | 我们不注册 |
| **通用组** | "这个进程里要装什么" | 我们 | 我们只注册这个 |

**为什么平台组不能碰**：

1. 一个进程只允许**一个**平台激活。厂商已经占了。
2. 我们再去注册，两个都声称"我能跑"时，本地会直接拒绝启动——整条栈起不来。
3. "我注册，但返回的还是厂商那个类"**不能免掉这个冲突**：冲突发生在"谁被激活"这一步，
   不在"返回的是谁的类"。
4. 收益是零：返回厂商的类等于什么都没做，却多背了一个会让全栈起不来的风险。

**通用组的行为**：上游在**每个进程**里调用一次（服务进程、引擎进程、每个 worker、
以及模型架构探测子进程）。由此得到两条必须遵守的事实：

1. **注册必须早于任何查表**——模型构造时会查表，表没写好就等于没接上。
2. **同一个函数会在同一台机器上被调用多次**（多进程），必须幂等。

**两个入口组的执行顺序不是契约。** 平台组在 `current_platform` 第一次被访问时才加载；
通用组在 `EngineArgs.__post_init__` / EngineCore / worker 里执行。当前 0.23 的 `vllm serve`
路径上通用组先跑（`vllm__engine__arg_utils.py:745` 早于 `:1712`），但别把它当保证——
我们真正依赖的只有一条：**包装早于第一次注意力后端查询**（见 §6 第 2 条）。平台先激活
还是后激活都不影响，因为我们包的是类方法，而平台对象就是那个类的实例。

## 3. 模型配置在什么时候能拿到

| 时机 | 能拿到什么 | 能不能做决策 |
|---|---|---|
| 命令行阶段（进程还没起） | 模型目录里的配置、本机能力 | ✅ 最好：能给人读的错误，能拒绝启动 |
| 插件入口（进程启动） | 环境变量、命令行残留、本机能力 | ⚠️ 只能"读计划、准备换表" |
| **模型加载前** | 完整模型配置 + 并行配置 + KV 预算 | ✅ **最后一次能安全改表的时机** |
| 算子实例化时 | 类名与构造参数 | ❌ 太晚，只能做局部断言 |
| 首次前向 | 真实形状 | ❌ 图可能已捕获 |

默认分工是：**命令行阶段做决策 → 落成计划文件 → 入口读计划 → 模型加载前用真配置
交叉校验 → 之后只做断言。**

但这是**取舍，不是物理限制**。两点必须说清：

1. 入口函数是无参的，所以"在插件入口里决策"确实拿不到模型配置——这是**入口位置**的限制，
   不是 vLLM 的限制。`vllm serve <model>` 的模型路径就在 `EngineArgs.model` 里
   （`reference/vllm-0.23/vllm__engine__arg_utils.py:415`），进程里拿得到。
2. `create_engine_config()` 返回时，`vllm_config.model_config` 已经完整；在那里决策在技术上
   完全可行（顺序上仍在模型构造之前，换表来得及），而且能消灭"计划给 A、serve 的是 B"。
   我们默认不在那里决策，理由是审计、回滚和 CI 门——见 §5 的红线表。

## 4. 六个接入点（按机制分类）

按"对象"数会更多，但同一机制接管多少个对象**不增加成本**——这是接入点按"机制"计数的原因。

| # | 机制 | 解决什么 | 越界的风险 |
|---|---|---|---|
| 1 | **实现替换表** | 算子、层：让上游的类名解析到我们的实现 | 低（官方机制）；同名冲突时是断言而非覆盖 |
| 2 | **方法包装** | 上游用普通函数或方法的地方（补第 1 项够不到的面） | 中：包错层级会静默失效 |
| 3 | **模型替换表** | 整个模型类（路线 O） | 低；同名会静默覆盖，必须留日志 |
| 4 | **注意力后端选择** | 决定用哪个注意力后端 | 中：上游有缓存，晚了无效 |
| 5 | **插件入口** | 让我们在正确时机被调用 | 低 |
| 6 | **图捕获钩子** | 捕获前完成桶规划、捕获后确认零回退 | 中：捕获后不可再改 |

**预算：已定义 6 个机制，设计上限 8 个。两个数字不是一回事：**

- **6** 是上面这张表、也就是 `contracts/plan.py` 里 `ACCESS_POINTS` 封闭列表的长度。
  计划文件里写第 7 个名字会被 `Plan.validate()` 直接拒绝——**部署期和启动期都不能新增机制**，
  只能从这 6 个里选子集（Qwen3.6 的计划只列了 4 个：入口、注意力选择、方法包装、图捕获）。
- **8** 是制度红线：只有当现有机制确实够不到某件事时，才允许改代码把第 7、8 个加进封闭列表，
  同时补上安装/校验/卸载/失效探测四件套，并写例外说明。超过 8 必须重新设计。
  这个数字是"还能每次上游升级都全量验证"的边界，不是"配置文件里还剩两个空位"。

所以：**"用了几个"（计划里的子集）和"定义了几个"（封闭列表 6）和"最多允许定义几个"（8）
是三件事**，别把 8 当成可填参数。

## 5. 入口函数的职责与红线

入口函数（install）只做一件事：**按计划把表换掉，并确认换上了。** 顺序固定：

```
1. 读计划 ──── 指定了 TILEINFER_PLAN 但文件不存在 → 直接返回（不注入，厂商原样跑）
               未指定 TILEINFER_PLAN → 用默认声明（TILEINFER_MANIFEST，默认 qwen3_6）现场
               算一份兜底计划；这是便利路径，它拿不到 --model，靠后面的 config gate 兜底
2. 版本门 ──── 与计划记录的三件套版本不一致 → 不注入
3. 显式开关 ── 被要求禁用 → 不注入
4. 按计划换表 ─ 已实现：注意力后端选择、config gate、图捕获计数；
               未实现：实现表 / 模型表（非 vendor 选择时明确返回失败，不猜）
5. 探测生效 ── 断言每一项真的换上了（不靠推理）
6. 查内核缓存 ─ **未实现**：`aot/` 还是空壳（M2 预编译门），当前运行期不查缓存
7. 记摘要 ──── 一行：注入了哪几项、跳过了哪几项、为什么
```

四条红线：

| 红线 | 原因 |
|---|---|
| **不在插件入口做决策** | 入口无参，此刻没有模型配置。这是**选择**：入口之后的 `create_engine_config` 已经能拿到真配置，可以决策；我们把它留在部署期，换的是可审计/可回滚（见 §3）。未设计划时的兜底只按默认声明算，不看现场模型——这正是 config gate 存在的理由 |
| **不编译内核** | 入口在每个进程都会跑；编译会占住解释器（实测能把引擎卡死） |
| **绝不向外抛异常** | 上游只 catch 模块导入，**不 catch 入口函数的执行**；抛出去 = 整个进程起不来 |
| **幂等且可卸载** | 多进程各跑一次；每个接入点都要能单独摘掉、单独验证 |

第三条最容易被忽略：**我们这层失效时，厂商路径必须照常能跑。** 所以内部兜住一切异常，
失败就记日志并返回"不注入"，而不是让异常穿出去。

## 6. 四个已知陷阱

0. **上游只 catch 导入，不 catch 执行。** 我们的包 import 失败 → 上游记日志继续（厂商照跑）；
   入口函数抛异常 → 进程直接起不来。见 §5 第三条红线。
1. **同名替换是断言，不是覆盖。** 上游生态里若已有同名实现（vllm-ascend 会注册一批），
   再注册会直接抛错。要么换名，要么直接写表——后者要收敛成**一个**函数，并在日志里写明"接管自谁"。
2. **注意力后端的选择有缓存，而且在模型构造时就查。** 每层 `Attention.__init__` 第一次
   调用 `get_attn_backend` 就把结果按 `(backend, 选择器配置, num_heads)` `@cache` 住；
   之后再包装，**对该配置永久无效**——不是等首次前向才失效。晚装的后果不是"没生效"这么
   干净：不同层配置不同，可能一半键被厂商类钉死、一半走了我们的，**一个模型里混两种后端**，
   而 KV 布局是全局的。
3. **子类覆盖会吃掉包装。** 昇腾上实际运行的是子类；若子类自己重写了我们要包的方法，
   包基类不生效。要么包实际类，要么在探测阶段发现。

## 7. 不靠相信，靠探测

换完表必须立刻验一遍，并在运行期计数：

| 探测 | 验什么 |
|---|---|
| 表项断言 | 我们写进去的条目确实是我们的实现 |
| 注意力后端 | 解析出来的类确实是我们 |
| 平台方法 | 被包装的方法确实换成了我们的 |
| 运行期打点 | 首次前向真的进了我们的实现（表对了但实例没创建是可能的） |
| 回退计数 | 稳态为 0；不为 0 就是缺陷 |

历史上出过"表写对了、进程里却看不到"的事故，原因至今没有完全定论。
**所以这一层不依赖推理，只依赖探测结果。**

## 8. 与 vllm-ascend 的分工

| 归它 | 归我们 |
|---|---|
| **平台槽位**（谁回答"这台机器是什么平台"） | 通用插件槽位 |
| 设备、上下文、流、worker、显存、KV 池分配、图捕获、通信 | 模型声明、决策、契约、实现提供者、内核 |
| 已经适配的模型与算子 | 它没适配的模型与算子 |
| 平台能力探测的**事实来源** | 用这些事实做选择 |

一条判据：**凡是"一个进程只能有一个"的东西，归它。** 平台就是这种东西。

---

## 9. 版本三角

引擎、平台、运行时三者的版本组合必须与计划文件里记录的一致。不一致就**不注入**并把差异打印出来——
不允许"先跑跑看"，因为不一致的表现通常是**数值错**而不是崩溃。

---

## 10. 和 v2 的关系

v2 的做法是自己实现平台层（不装 vllm-ascend），因此它必须占住平台槽位。
v3 把这个前提反过来：**平台槽位归上游，我们只占通用槽位。**

v2 的接入经验仍然有效（哪些地方必须 hook、哪些地方 hook 了也没用），
但代码形态不作数——`tileinfer/vllm/` 已归档到 `legacy/v2/`，v3 的接入形态是
`tileinfer/bridge/`（见 [`architecture.md`](architecture.md) 的 L5 与
[`development-rules.md`](development-rules.md) §3）。
