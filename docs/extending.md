# 扩展指南

> 回答一个问题：**要加东西的时候，改哪儿、按什么顺序、怎么算加完了。**
> 不含代码骨架——骨架会随实现变，规则不会。

---

## 0. 三个扩展点

| 扩展点 | 加什么 | 谁需要它 | 成本量级 |
|---|---|---|---|
| **A 模型声明** | 一个新模型"需要什么"（结构、注意力风味、KV 分组、量化、依赖的能力、基准样例） | 想做路线 U 或 O 的人 | 一份声明 |
| **B 实现提供者** | 厂商缺口的一条具体实现（自研内核 / 引入的代码 / 参考实现）；厂商原生的只"选"不"供" | 缺口清单上有条目的人 | 一条实现 + 证据 |
| **C 接入点** | 让上游在某个位置使用我们的东西 | **只在现有 6 个机制不够用的时候** | 一次架构决策 |

顺序是硬的：**先有声明，才有缺口清单；缺口清单决定要写哪些提供者；接入点最后。**

---

## 1. 三条共同规则

1. **单向依赖**：契约层不知道提供者，提供者不知道决策层，内核层不知道引擎。
   任何反向依赖都不是风格问题，而是会让"能不能测"变成"只能上卡试"。
2. **无静默回退**：加东西的时候，任何"不支持就走原路"的代码都必须留下计数与日志。
   静默回退的表现只是变慢，没有告警，等于没做。
3. **没有证据不算加完**：最小证据是"一条可复现的运行 + 一个数"。**有基线时那个数是比值，
   没有基线时是绝对性能 + 与参考实现的一致性**——口径见 [`acceptance.md`](acceptance.md) §2.1。
   没有证据的条目只能停在"候选"，不能进默认路径。

---

## 2. 扩展点 A：模型声明

**它是什么**：用一份声明描述"这个模型需要什么"，让决策层能在**不加载权重、不上卡**的情况下
算出缺口清单。这是整套扩展性的支点——没有它，新模型就只能靠"跑一遍看哪炸"。

**必须写进去的六件事**：

| 项 | 为什么必需 |
|---|---|
| 结构标识（模型家族、层数、每层是什么类型） | 决定走路线 U 还是 O |
| 注意力风味序列（哪些层是全注意力、哪些是线性注意力、各自参数） | 这是每模型最大的成本项 |
| KV 分组（几组池、页大小约束、是否混合） | 不同家族的 KV 形态不可混用 |
| 量化方案 | 与模型正交，但决定能不能加载 |
| 依赖的能力清单 | 决策层据此逐条比对现场能力 |
| 基准样例（同一请求的期望输出） | 没有它就判不了"跑对" |

**验收**：声明能通过结构校验；决策层能凭它产出缺口清单；清单里的每一条都能对应到一个提供者。

**不能改的**：决策流程本身。模型声明只描述"需要什么"，不许在里面写"该用谁的实现"——
那是决策层的输出，写进声明就等于把策略焊死在数据里。

---

## 3. 扩展点 B：实现提供者

### 3.0 只补缺口

**提供者存在的唯一理由是"厂商这条能力用不了"。** 判据不是"我们能不能更快"，而是：

> 厂商这条路径**能跑、能跑对、能上图**吗？三者都满足 → 选厂商，不写提供者。

再写一遍厂商已经做好的事，就是把别人的活重做一遍——v2 用 TPOT 2.53× 付过这笔账。
所以 `providers/` 的规模应该随**厂商缺口数**增长，而不是随"能部署的模型数"增长。
一个直接的自检：**如果某条 provider 的删除条件是"永远不删"，那它多半根本不该存在**
（参考实现 / oracle 例外，它们本来就不进默认路径）。

缺口有四种形态，只有前三种由本层补：

| 缺口 | 表现 | 谁补 |
|---|---|---|
| **缺失** | 厂商根本没有这条实现 | L4 提供者 |
| **子集** | 厂商有实现，但目标形状 / 精度 / 头维度不支持 | L4 提供者（可只覆盖这个子集） |
| **不合格** | 厂商能跑，但该形状数值不对 | L4 提供者（正确性优先于速度） |
| **不可图** | 厂商能跑对，但该路径无法图捕获 | bridge 的接入点，**不是**提供者 |

**它是什么**：一个能力契约的一条实现。三条来源：自研、引入（带来源与许可）、参考实现。
"厂商原生"不是本层的来源——它是决策层可以直接选的条目（`resolve/vendor.py`），
进计划表，不进 `providers/`。

**每条提供者必须自带五条声明**：

| 声明 | 用途 | 没有基线时怎么填 |
|---|---|---|
| 覆盖范围（形状符号、精度、头部维度等） | 决策层据此匹配；**用符号表达，不用具体数值** | 同左 |
| 能否上图 | 不能上图的能力不能进稳态默认路径 | 同左 |
| 并行度（支持哪些切分） | 现在只有单卡，但字段要留 | 同左 |
| 证据编号 | **没有证据不许进默认路径**；有基线时证据里带同一窗口的比值 | 绝对数 + 与参考实现逐位/容差一致的记录 |
| **删除条件** | 什么条件下这条实现应该被删掉（通常是上游补齐了某能力） | 同左 |

> `measured_ratio` 因此在无基线时**留空**，但**证据不能留空**。
> 空证据的提供者是"感觉能用"，不是"验证过能用"。

**验收**：正例一条、负例一条（"我声明不支持"必须能被验证）；数值与参考实现对得上；
可上图的能力要给出捕获成功的证据；有基线时给同窗口成对比值，无基线时给绝对数，
外加一条"厂商为什么用不了"的复现记录。

**两条容易踩的**：

- **契约粒度决定能不能融合**。按数学算子切（卷积、扫描、矩阵乘各一条契约），融合就被禁止了；
  按"融合后的单元"切才对。收益来自减少发射与搬运，不是单个算子变快。
- **只有一个提供者的契约是抽象税**。要么等第二个来源出现，要么把它合并回模型层。

## 4. 扩展点 C：接入点

**只在现有 6 个机制不够用时才加。** 加一个就要在预算里占一格（上限 8）。

一份合格的接入点必须带四件东西：

| 件 | 要求 |
|---|---|
| 安装 | 幂等；可被显式关闭 |
| 校验 | 装完立刻能断言"确实生效"，不靠推理 |
| 卸载 | 能恢复原状；测试要跑这条路径 |
| 失效探测 | 上游改了导致静默失效时，能被发现（而不是表现为变慢） |

**判断规则**：什么该固定、什么该可插拔？

> **凡是"选择"可插拔，凡是"顺序/时序"固定。**

例如：用哪个实现可插拔；但"先决策、再落表、再捕获"的顺序不许可插拔——
顺序一乱，问题会以性能或数值的形式出现在别处，极难归因。

## 5. 现在还不能扩展的

| 项 | 现状 | 什么时候做 |
|---|---|---|
| 并行（TP/EP/PP） | 单卡 | 有第二张卡再谈 |
| 量化方案 | bf16 一条路 | 有明确模型需求时，按模型逐个开 |
| 混合批 / 投机解码 | 只支持单 query token | 视作"注意力契约扩展"，单独一轮 |
| 新硬件 | 只有昇腾 950 | 出现第二块卡时加一组提供者；**只有那块卡没有厂商平台时**，才由我们提供平台（昇腾不属于这种情况） |

## 6. 加东西的检查清单

- [ ] 写声明（扩展点 A），跑通决策，拿到缺口清单
- [ ] 缺口清单排期；每一条对应一个提供者（扩展点 B），并先确认厂商在这一条上**真的不能用**
- [ ] 提供者带五条声明，正负例测试各一
- [ ] 需要新接入点时，先问"能不能用现有 6 个"；不能，再走扩展点 C
- [ ] 四道门：能跑 / 跑对 / 能上图 / 跑快；无基线时 C2/C4 走绝对口径（[`acceptance.md`](acceptance.md) §2.1）
- [ ] 落证据，状态改"在役"；同时在声明里写下**删除条件**
