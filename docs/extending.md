# 扩展指南

> 回答一个问题：**要加东西的时候，改哪儿、按什么顺序、怎么算加完了。**
> 不含代码骨架——骨架会随实现变，规则不会。

---

## 0. 三个扩展点

| 扩展点 | 加什么 | 谁需要它 | 成本量级 |
|---|---|---|---|
| **A 模型声明** | 一个新模型"需要什么"（结构、注意力风味、KV 分组、量化、依赖的能力、基准样例） | 想做路线 U 或 O 的人 | 一份声明 |
| **B 实现提供者** | 厂商缺口的一条具体实现（自研内核 / 引入的代码 / 参考实现）；厂商原生的只"选"不"供" | 缺口清单上有条目的人 | 一条实现 + 证据 |
| **C 接入点** | 让上游在某个位置使用我们的东西 | **只在现有 6 个机制不够用的时候** | 一次架构决策 |

顺序是硬的：**先有声明，才有缺口清单；缺口清单决定要写哪些提供者；接入点最后。**

---

## 1. 三条共同规则

1. **单向依赖**：契约层不知道提供者，提供者不知道决策层，内核层不知道引擎。
   任何反向依赖都不是风格问题，而是会让"能不能测"变成"只能上卡试"。
2. **无静默回退**：加东西的时候，任何"不支持就走原路"的代码都必须留下计数与日志。
   静默回退的表现只是变慢，没有告警，等于没做。
3. **没有证据不算加完**：最小证据是"一条可复现的运行 + 一个数"。**有基线时那个数是比值，
   没有基线时是绝对性能 + 与参考实现的一致性**——口径见 [`acceptance.md`](acceptance.md) §2.1。
   没有证据的条目只能停在"候选"，不能进默认路径。

## 2. 扩展点 A：模型声明

**它是什么**：用一份声明描述"这个模型需要什么"，让决策层能在**不加载权重、不上卡**的情况下
算出缺口清单。这是整套扩展性的支点——没有它，新模型就只能靠"跑一遍看哪炸"。

**必须写进去的六件事**：

| 项 | 为什么必需 |
|---|---|
| 结构标识（模型家族、层数、每层是什么类型） | 决定走路线 U 还是 O |
| 注意力风味序列（哪些层是全注意力、哪些是线性注意力、各自参数） | 这是每模型最大的成本项 |
| KV 分组（几组池、页大小约束、是否混合） | 不同家族的 KV 形态不可混用 |
| 量化方案 | 与模型正交，但决定能不能加载 |
| 依赖的能力清单 | 决策层据此逐条比对现场能力 |
| 基准样例（同一请求的期望输出） | 没有它就判不了"跑对" |

**验收**：声明能通过结构校验；决策层能凭它产出缺口清单；清单里的每一条都能对应到一个提供者。

**不能改的**：决策流程本身。模型声明只描述"需要什么"，不许在里面写"该用谁的实现"——
那是决策层的输出，写进声明就等于把策略焊死在数据里。

## 3. 扩展点 B：实现提供者

### 3.0 只补缺口

**提供者存在的唯一理由是"厂商这条能力用不了"。** 判据不是"我们能不能更快"，而是：

> 厂商这条路径**能跑、能跑对、能上图**吗？三者都满足 → 选厂商，不写提供者。

再写一遍厂商已经做好的事，就是把别人的活重做一遍——v2 用 TPOT 2.53× 付过这笔账。
所以 `providers/` 的规模应该随**厂商缺口数**增长，而不是随"能部署的模型数"增长。
一个直接的自检：**如果某条 provider 的删除条件是"永远不删"，那它多半根本不该存在**
（参考实现 / oracle 例外，它们本来就不进默认路径）。

缺口有四种形态，只有前三种由本层补：

| 缺口 | 表现 | 谁补 |
|---|---|---|
| **缺失** | 厂商根本没有这条实现 | L4 提供者 |
| **子集** | 厂商有实现，但目标形状 / 精度 / 头维度不支持 | L4 提供者（可只覆盖这个子集） |
| **不合格** | 厂商能跑，但该形状数值不对 | L4 提供者（正确性优先于速度） |
| **不可图** | 厂商能跑对，但该路径无法图捕获 | bridge 的接入点，**不是**提供者 |

**它是什么**：一个能力契约的一条实现。三条来源：自研、引入（带来源与许可）、参考实现。
"厂商原生"不是本层的来源——它是决策层可以直接选的条目（`resolve/vendor.py`），
进计划表，不进 `providers/`。

**能力不是算子。** 8 个 capability 是**契约粒度**，一个能力可以覆盖一组算子：`attention.linear`
覆盖 GDN 的 chunk / recurrent 两条路径，底层涉及 conv / gating / kkt / wu / solve_tril /
delta_h 一组算子（状态读写归 `state.linear`）。能力→算子的绑定分两段：`ProviderSpec.impl`
给出实现位置（类路径或模块），`covers` 给出覆盖范围；真正写进引擎的落点由接入点决定——
注意力后端走 `attn_select`，算子/层走 `impl_table`，整模型走 `model_table`。

**当前已接通的接入点**：`attn_select` 会查计划里的 `attention.full`；`impl_table` 由
`tileinfer/bridge/impl_table.py` 按计划里的**非厂商 selection**逐条安装 provider。两者在
vendor 选择下都返回厂商原路径，不做任何替换。`impl_table` 不维护全局算子表，也不允许
"看到非厂商选择就先装一遍"；没有 `impl_table` 接入点、没有对应 selection、或 provider 名
未知，都必须失败而不是猜。`model_table` 已由 MuseGlimmer（模型 + parser）和 LFM3
（模型 + `register_config`）使用，不再是空实现。

当前 L4 的声明包括 LFM3 的 `tileinfer.short_conv`（模型作用域、由模型内部消费）和
Nemotron 的两个**候选**：`tileinfer.mamba2_state`、`tileinfer.nemotron_moe`。候选可以在
显式构造的 bring-up 计划里被选中并测试安装，但不会自动进入默认计划；真权重 C1/C2 通过前，
Nemotron 的计划仍是 `servable=false`。

**Provider 生命周期字段（P0）**：选择不再由 seam 认识 provider 名字决定，而是由声明决定：

| 字段 | 值 | 作用 |
|---|---|---|
| `status` | `default` / `candidate` | `candidate` 只能经 `allow_candidates` 的 bring-up 进入计划，计划仍 `servable=false` |
| `scope` | `global` / `model` | `model` 只在声明了 `model_impl` 的模型内生效，避免 short-conv 误选 Qwen 的 GDN |
| `install` | `impl_table` / `model_impl` / `vendor_hook` | 装进算子表、由我们的模型直接调用，或通过 vendor 钩子生效 |
| `graph_safe` | `bool` | 已实测图捕获/replay/无 host 同步，而不仅是“形状上可图” |
| `evidence_level` | `candidate` / `cpu` / `device-c1..c4` / `verified` | 机器可读的证据成熟度，和自由文本 `evidence` 分开 |

`install_impl_table()` 不再硬编码 `tileinfer.short_conv`：它按 `ProviderSpec.install` 跳过
模型内部消费的 provider，只把真正的算子表条目交给 binder。

**P1 共享工具**：模型接入的重复劳动已经收敛到三个位置：

| 工具 | 位置 | 解决的问题 |
|---|---|---|
| `WeightMapSpec` | `tileinfer/bridge/weight_map.py` | 声明 rename / stacked qkv·w13 / skip prefix / expert remap / FP32 前缀，`load_weights()` 统一执行 |
| `StateLayout` | `tileinfer/models/state_layout.py` | 计算逻辑 state、Ascend 页对齐后的 shape、blocks；LFM3 short-conv 已完成迁移 |
| `CompatHook` | `tileinfer/bridge/compat_hooks.py` | 统一登记 vendor monkeypatch / platform guard / rope patch / model-side numeric fix，带 disable env、delete_when 和 evidence；Nemotron/LFM3 已接入 |

### 3.5 v2 归档规则（硬约束）

**`tileinfer/vllm/` 已于 2026-11-16 归档到 `legacy/v2/tileinfer/vllm/`；它不在安装包内，
也不可 import。** v3 不再保留 v2 兼容 shim。

- 不在 `legacy/v2/` 新增/修改实现；那里只是历史参照。
- v3 模块不得 import `tileinfer.vllm`；`import tileinfer.vllm` 现在应当失败。
- 新算子/适配器放 `tileinfer/providers/`（L4），只 import torch/契约；需要 import vLLM
  或 vllm-ascend 的安装代码放 `tileinfer/bridge/`（L5）。
- 新模型必须有 `ModelManifest`（不是 v2 的 `ModelProfile`）；不能靠"默认声明 + 改一个
  family"跑起来。模型相关事实写 manifest，算子到 vLLM 名字的绑定写 bridge 的显式表。
- 计划是唯一安装依据：`Plan.servable=false` 时默认拒绝安装非厂商 provider；只有显式
  `TILEINFER_ALLOW_UNSERVABLE=1` 的 bring-up 运行可以覆盖，且必须打日志、不能进产品路径。
- 新增 v3 路径必须带一条"没有 v2 import"的测试；review 看到 `legacy/v2/` 业务改动或
  重新引入 `tileinfer.vllm` 应直接拒绝。

**每条提供者必须自带五条声明**：

| 声明 | 用途 | 没有基线时怎么填 |
|---|---|---|
| 覆盖范围（形状符号、精度、头部维度等） | 决策层**目前只用 `mixer` 键**做匹配（GDN vs Mamba2）；`head_dim`/`dtype` 等键是证据元数据，不参与路由 | 同左 |
| 能否上图 | 不能上图的能力不能进稳态默认路径 | 同左 |
| 并行度（支持哪些切分） | 现在只有单卡，但字段要留 | 同左 |
| 证据编号 | **没有证据不许进默认路径**；有基线时证据里带同一窗口的比值 | 绝对数 + 与参考实现逐位/容差一致的记录 |
| **删除条件** | 什么条件下这条实现应该被删掉（通常是上游补齐了某能力） | 同左 |

> `measured_ratio` 因此在无基线时**留空**，但**证据不能留空**。
> 空证据的提供者是"感觉能用"，不是"验证过能用"。

**匹配的现状：名字级 + mixer 级，不是形状级。** `decide()` 只判断两件事——能力名在
`VENDOR_PROVIDERS` 里有没有条目；`covers["mixer"]` 是否命中（GDN vs Mamba2）。manifest 里
已有的 `head_dim` / `num_kv_heads` / `top_k` / `quantization` 还没有写成谓词，也不参与选择。
所以计划期的"能力具备"只等于"名字有主"；具体形状能不能跑，由厂商在模型构造时判断，
失败表现为运行时异常或静默降级。

**验收**：正例一条、负例一条（"我声明不支持"必须能被验证）；数值与参考实现对得上；
可上图的能力要给出捕获成功的证据；有基线时给同窗口成对比值，无基线时给绝对数，
外加一条"厂商为什么用不了"的复现记录。

**两条容易踩的**：

- **契约粒度决定能不能融合**。按数学算子切（卷积、扫描、矩阵乘各一条契约），融合就被禁止了；
  按"融合后的单元"切才对。收益来自减少发射与搬运，不是单个算子变快。
- **只有一个提供者的契约是抽象税**。要么等第二个来源出现，要么把它合并回模型层。

## 4. 扩展点 C：接入点

**只在现有 6 个机制不够用时才加，而且"加"是改代码，不是改配置。** 具体动作是：往
`contracts/plan.py` 的 `ACCESS_POINTS` 封闭列表里加一项，补安装/校验/卸载/失效探测四件套，
并占一格预算（上限 8）。计划文件里凭空写一个新机制会被 `Plan.validate()` 拒绝——部署期
只能从已定义的机制里选子集。

一份合格的接入点必须带四件东西：

| 件 | 要求 |
|---|---|
| 安装 | 幂等；可被显式关闭 |
| 校验 | 装完立刻能断言"确实生效"，不靠推理 |
| 卸载 | 能恢复原状；测试要跑这条路径 |
| 失效探测 | 上游改了导致静默失效时，能被发现（而不是表现为变慢） |

**判断规则**：什么该固定、什么该可插拔？

> **凡是"选择"可插拔，凡是"顺序/时序"固定。**

例如：用哪个实现可插拔；但"先决策、再落表、再捕获"的顺序不许可插拔——
顺序一乱，问题会以性能或数值的形式出现在别处，极难归因。

## 5. 现在还不能扩展的

| 项 | 现状 | 什么时候做 |
|---|---|---|
| 并行（TP/EP/PP） | 单卡 | 有第二张卡再谈 |
| 量化方案 | bf16 一条路 | 有明确模型需求时，按模型逐个开 |
| 混合批 / 投机解码 | 只支持单 query token | 视作"注意力契约扩展"，单独一轮 |
| 新硬件 | 只有昇腾 950 | 出现第二块卡时加一组提供者；**只有那块卡没有厂商平台时**，才由我们提供平台（昇腾不属于这种情况） |

## 6. 加东西的检查清单

- [ ] 写声明（扩展点 A），跑通决策，拿到缺口清单
- [ ] 缺口清单排期；每一条对应一个提供者（扩展点 B），并先确认厂商在这一条上**真的不能用**
- [ ] 提供者带五条声明，正负例测试各一
- [ ] 需要新接入点时，先问"能不能用现有 6 个"；不能，再走扩展点 C
- [ ] 四道门：能跑 / 跑对 / 能上图 / 跑快；无基线时 C2/C4 走绝对口径（[`acceptance.md`](acceptance.md) §2.1）
- [ ] 落证据，状态改"在役"；同时在声明里写下**删除条件**
