# 性能对比规则（A/B 前提）

一旦做任何"我方 vs 基线"的数字对比，**两臂必须运行在同一套环境里**。这条是硬约束，
不是建议：本仓已经出过一次不可比的结果。

## 必须逐项一致的项

| 项 | 为什么必须一致 |
|---|---|
| torch / torch_npu 版本 | 同一内核在不同 torch 上差异可达数十个百分点（实测见过 2.10 与 2.13 的算子实现不同） |
| vLLM 版本 | 调度与算子选择随版本变化 |
| tilelang 版本与 `TILELANG_CACHE_DIR` | 决定内核是否命中缓存、是否重新编译 |
| CANN 版本与 `ASCEND_HOME_PATH` | 编译器与算子库不同 |
| 启动参数 | `--max-model-len`、`--max-num-seqs`、`--max-num-batched-tokens`、`--gpu-memory-utilization`、eager/graph |
| 模型目录 | 同一份权重 |
| 卡状态 | 同一张卡、无人占用、同样的 `npu-smi` 显存占用 |
| 测量方法 | 同一脚本、同一 prompt、同一 `max_tokens`、同样的 warmup 与重复次数 |

## 已知的不可比反例（不要重复）

2026-11-03 的一次 A/B：我方臂用 `tileinfer` venv（torch 2.10.0+cpu / torch_npu 2.10.0.post4），
基线臂用现成的 `/home/dlb/.venv_ascend`（torch 2.13.0+cpu / torch_npu 2.13.0rc1）。
数字虽然量级差异明显（TPOT 3.5×），但**只能作为方向性证据，不能作为结论**。

## 正确做法

1. 用同一 venv 跑两臂：先装我方（`pip install -e .`）跑我方；`pip uninstall -e .` 后再装基线跑基线；
   或复制同一 venv 做两次安装（`cp -a .venv .venv_baseline`，再分别 pip 卸载/安装）。
2. 每次测量前记录 `pip list | grep -Ei 'torch|vllm|tilelang'` 与 `npu-smi info` 到结果文件头部。
3. 用 `benchmarks/ab_report.py --check` 确认两臂都 ready、无 fallback、非 cold 后再比对。

## 2026-11-03 追加：TPOT 怎么测，以及为什么必须交替跑

### TPOT 只能用差分法

```
tpot = (T(N2) - T(N1)) / (N2 - N1)      N1=8, N2=72, 同一 prompt, 非流式, 重复 3 次取中位数
```

实现：`benchmarks/wall_tpot.py`。同一 prompt 下提示词成本、首 token 成本、每请求开销与客户端延迟
都在两项里出现并相消，剩下的才是"多一个 token 的边际成本"。

**不要**再用以下两种，它们在这个后端上互相矛盾过：
- 流式分块间隔（chunk delta）：曾给出 0.138–0.166 s/token，而端到端只有 0.082；
- `(total - ttft) / n`：把首 token 成本摊进每 token，`64 token / 5.255 s` 推出的 "82 ms" 就是这么来的，
  换成差分法后同一配置是 118–163 ms。

### 必须交替两臂，并记录温度

实测：**同一台机器、同一个服务进程，前后两次调用差 37%**（118.5 → 163.0 ms/token），
期间 `npu-smi` 显示 73–75 ℃、282–313 W、util 95%；而 baseline 两次测量之间只差 2.5%。
判断是持续负载后的降频，而不是代码变化。

因此：
1. 顺序必须是 **A→B→A**，用第二个 A 判定漂移；只跑 A 再跑 B 得到的差异不可信；
2. 每次测量记录 `npu-smi info` 的**温度与功率**，写进结果文件头部；
3. 小于 10% 的改动，除非在同一进程内做 op 级 A/B（没有降频变量），否则**不下结论**；
4. 报结果时必须同时报**极差**（`wall_tpot.py` 会打印），没有极差的"提升 3%"无法与噪声区分。

### 非物理解必须作废，不能进中位数

`t(N2) < t(N1)`（即负的每 token 时间）不可能发生在同一路径上，出现就说明这次采样坏了
（设备被抢、请求被重试、分块卡住）。`benchmarks/paired_tpot.py` 已把这条做成硬规则：
`measure()` 直接抛错，该对作废并重试，最多 `3 × PAIRS` 次，末尾报"有效对 / 作废对"。

这条是买来的：§34 有一对给出 `off = −1378 ms/token`，把整体 ratio 从 ~1.06 拉到 1.028。

### 这台机器是**共享**的

2026-11-03 实测：另一个用户（`/home/userlist/ww/test_infer_engine`）会用**本仓库的 venv**
起 serve，占着同一张卡（一次观测到 89 GB），此后吞吐掉 2–4×，且能让单次配对测量自相矛盾。

因此：

1. 每次测量前检查 `npu-smi` 的进程表，**不只看我们自己的进程**；有外部进程就记录下来，
   并优先等一个独占窗口，而不是"凑合测"。
2. 外部负载能解释的方差，不要归因成代码或"设备降频"（§29 曾把外部负载误记成自己的孤儿进程）。
3. 本仓库是 editable 安装 —— 我们的 `scp` 同步会直接改动对方正在依赖的代码树。
   这需要协作层面的约定（独占窗口，或各自一份仓库/venv），不能靠单方面小心。
